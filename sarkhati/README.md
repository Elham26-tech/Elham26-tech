# سرخطی‌زن

ابزار محلیِ ارسال سفارش در لحظهٔ بازگشایی بازار. **بدون نصب** — روی فایل
`Sarkhati.bat` دوبار کلیک می‌کنید، یک پنجرهٔ مشکی با یک لینک باز می‌شود، روی لینک
می‌زنید و صفحهٔ کنترل کنار دستتان باز می‌شود. هیچ پکیجی نصب نمی‌شود؛ فقط Node.js
(نسخهٔ ۱۸ به بالا، یک‌بار از nodejs.org) و کروم/اِجِ خودِ ویندوز لازم است.

## روش کار

```
۱  «باز کردن ایزی تریدر»  →  کروم با صفحهٔ کارگزاری باز می‌شود
۲  خودتان لاگین می‌کنید، نماد را جست‌وجو و یک بار دستی خرید/فروش می‌زنید
۳  برنامه همان سفارش واقعی را یاد می‌گیرد  ✓
۴  تعداد/قیمت امروز و ساعت هدف را می‌دهید و «مسلح کردن» را می‌زنید
```

نام کاربری و رمز کارگزاری **هیچ‌وقت وارد این برنامه نمی‌شود**؛ لاگین داخل خودِ
پنجرهٔ کروم انجام می‌شود و نشست فقط در پروفایل کروم (`data/chrome-profile`) می‌ماند.

## سه باگی که رفع شده

### ۱. ماندن حافظهٔ اجرای قبلی بعد از باز کردن دوبارهٔ برنامه

داده‌ها به سه لایهٔ جدا تقسیم شده‌اند (`lib/store.js`):

| لایه | فایل | عمر |
|---|---|---|
| تنظیمات | `data/settings.json` | ماندگار |
| وضعیت جلسه (مسلح بودن، تلاش‌ها، گزارش) | `data/session.json` | فقط همان روز معاملاتی |
| سفارش یادگرفته‌شده | `data/learned.json` | ماندگار، با دکمهٔ فراموشی |

وضعیت جلسه با کلید روز معاملاتی ذخیره می‌شود؛ اگر روزِ ذخیره‌شده با امروز فرق کند
موقع بالا آمدن دور ریخته می‌شود. حتی در همان روز هم «مسلح بودن» و «در حال یادگیری»
به اجرای بعدی به ارث نمی‌رسند تا برنامه بعد از ری‌استارت خودبه‌خود شلیک نکند. رابط
کاربری چیزی در `localStorage` نگه نمی‌دارد.

### ۲. خطای `HTTP 400 — Order.Side ... سفارش معتبر نمی‌باشد`

این خطا وقتی رخ می‌داد که برنامه خودش بدنهٔ سفارش را می‌ساخت و مقدار `Side` را حدس
می‌زد. حالا اصلاً حدسی در کار نیست (`lib/recipe.js`):

- درخواستِ سفارشی که **خودتان دستی ثبت می‌کنید** از داخل مرورگر ضبط می‌شود، ولی
  فقط وقتی کارگزاری آن را با کد ۲xx پذیرفته باشد.
- همان آدرس، همان نام فیلدها و **همان مقدار `Side`ای که کارگزاری پذیرفت** ذخیره
  می‌شود؛ موقع تکرار فقط تعداد/قیمت/نماد جایگزین می‌شوند و نوع فیلد (عدد یا رشته)
  هم حفظ می‌گردد.
- تکرار از داخلِ خودِ صفحهٔ کارگزاری انجام می‌شود، پس کوکی و توکن نشست دقیقاً
  همان‌هایی‌اند که مرورگر می‌فرستد و هدرهای ناپایدار بازتولید نمی‌شوند.

### ۳. شروع نشدن قبل از بازگشایی

```
لحظهٔ شروع شلیک = ساعت هدف − preArmSeconds + اختلاف ساعت سرور
```

`preArmSeconds` پیش‌فرض ۶۰ ثانیه است، پس اگر کارگزاری یک دقیقه زودتر باز کند
تلاش‌ها از قبل در جریان‌اند و اولین سفارشِ پذیرفته‌شده کار را تمام می‌کند.
«همگام‌سازی ساعت» اختلاف ساعت سیستم با سرور کارگزاری را اندازه می‌گیرد و در همین
محاسبه اعمال می‌شود.

## ساختار

```
sarkhati/
├─ Sarkhati.bat     اجرای بدون نصب (پنجرهٔ مشکی + لینک)
├─ server.js        سرور محلی ۹۱۱۷ و API
├─ lib/ws.js        کلاینت وب‌سوکت کمینه، بدون وابستگی
├─ lib/browser.js   باز کردن کروم و پروتکل DevTools
├─ lib/recipe.js    یادگیری و بازسازی سفارش            (باگ ۲)
├─ lib/store.js     سه لایهٔ داده و کلید روز معاملاتی    (باگ ۱)
├─ lib/engine.js    ساعت، شروع زودهنگام، حلقهٔ شلیک     (باگ ۳)
├─ public/          صفحهٔ کنترل (فارسی/RTL)
└─ test/            run.js (۱۶ تست) و e2e.js (تمرین با کروم واقعی)
```

## تست

```bash
npm test          # ۱۶ تست واحد
npm run test:e2e  # کارگزاری قلابی + کروم واقعی: یادگیری، تکرار، شروع زودهنگام
```

## نکته‌ها

- ساعت هدف با ساعت محلی همان کامپیوتر حساب می‌شود؛ منطقهٔ زمانی ویندوز را روی
  `Asia/Tehran` بگذارید.
- اگر کروم در مسیر غیرعادی نصب است، مسیرش را در متغیر `SARKHATI_CHROME` بدهید.
- نرخ ارسال را متناسب با قواعد کارگزاری خودتان تنظیم کنید.
- `data/` در گیت نادیده گرفته شده تا نشست کارگزاری هرگز commit نشود.
